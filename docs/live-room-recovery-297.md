# 1.7.297 — live room state and connection recovery

Lamp switches and the existing room registers now have an encrypted Drive fallback alongside the interactive motion fallback. Previously, a device without a direct RTC route could receive a moving book but wait for the durable library upload to receive a lamp switch or the final room state. A separate, bounded `live-state-v1-<peer>.json` file carries the latest full checkpoint; the small rendezvous mailbox references its revision. Updates coalesce, unchanged state is not repeatedly uploaded, and account-bound AES-GCM protects both fallback paths. Rust validates sender, account, register schema and packet size, and shares deduplication with the direct path.

Initial discovery retries independently of the library backup. Backgrounding suspends the connection while retaining its latest state; foregrounding and `pageshow` restart it. An established RTC session no longer stops merely because its HTTP access token expires. Both data channels must be open before a peer counts as connected. Monotonic heartbeat checks replace silent or incomplete connections, and negotiation retries use bounded backoff. Failed state application stays queued, failed mailbox reads can retry the same revision, and stale peers still expire. Discovery selects the newest duplicate mailbox, while only a confirmed HTTP 404 creates a replacement file.

Drive requests now have browser cancellation deadlines (20 seconds for metadata/state, five minutes for book downloads and uploads); existing OAuth cancellation remains intact. Large books keep a longer transfer window. Mailbox writes retain only an in-flight request and the latest follow-up instead of accumulating a heartbeat queue.

Verification covers startup failure, background/foreground recovery, missing or silent interactive channels, failed reads and local writes, duplicate mailboxes, HTTP deadlines, encrypted lamp state and bounded write queues. Chromium integration tests use two isolated browser contexts, simulated Drive (including private OAuth app properties and delayed durable uploads), and actual RTC channels through a local test TURN server. They check lamp changes in both directions, channel replacement, background resume, held touch dragging, identical final poses, and preservation of the shelf DOM/canvas. Separate cases block RTC completely and check encrypted state and held-motion delivery through Drive.

These are controlled integration tests, not measurements on the user's mobile network. Drive fallback latency depends on network/API response times; this change does not provision production TURN or promise frame-by-frame delivery on every network. If web OAuth expires while no RTC route exists, the user still needs to reconnect Google Drive; no silent web OAuth refresh or unsolicited sign-in popup is introduced. Android update channels and APKs are unchanged.
